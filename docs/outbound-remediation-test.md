# Outbound Threat Detection and NACL Remediation Test

## 1. Test Objective

Validate the outbound threat detection and remediation workflow using Suricata, the alert parser, a Python Lambda handler, and LocalStack's EC2 Network ACL API.

The test used controlled documentation IP addresses. No real command-and-control server or malicious external destination was contacted.

## 2. Suricata Detection

Suricata detected a controlled outbound TCP connection attempt to port 4444.

| Field | Result |
|---|---|
| Source IP | 10.106.155.63 |
| Destination IP | 198.51.100.77 |
| Destination port | 4444 |
| Direction | Outbound |
| Protocol | TCP |
| Signature ID | 1000005 |
| Severity | 1 |
| Interface | enp0s3 |
| Alert action | Allowed |

The alert confirmed that Suricata was monitoring the Ubuntu VM's enp0s3 interface.

The alert was generated by a local suspicious-port detection rule. It indicates suspicious activity, not confirmed command-and-control communication.

## 3. Parser Validation

The parser successfully extracted the alert information from Suricata EVE JSON.

The parser correctly classified the traffic as outbound and retained the source IP, destination IP, destination port, signature ID, severity, and interface.

The corrected parser output was saved in:

`logs/outbound_detection_test_v2.json`

## 4. Lambda DRY_RUN Validation

A separate synthetic severity-1 outbound alert was submitted to the Lambda handler.

| Field | Result |
|---|---|
| Source IP | 10.106.155.63 |
| Destination IP | 203.0.113.77 |
| Direction | Outbound |
| Severity | 1 |
| Handler status | DRY_RUN |
| Target IP selected | 203.0.113.77 |
| NACL modified by handler | No |

The handler correctly selected the destination IP for outbound containment.

Automatic containment remained disabled throughout the test.

## 5. Direct NACL Remediation Function Test

The remediation function was then called directly with the validated destination IP object.

LocalStack successfully accepted the outbound DENY rule creation request.

| Field | Result |
|---|---|
| Network ACL ID | acl-d636745fd2155230f |
| Test subnet ID | subnet-00756e574718220ef |
| Rule number | 101 |
| Direction | Outbound (egress) |
| Action | DENY |
| Blocked destination | 203.0.113.77/32 |
| Protocol | All traffic |
| API result | Successful |

## 6. Independent NACL Verification

A subsequent `describe-network-acls` request independently confirmed that the new rule was saved.

Verified entry:

`101 | True | deny | 203.0.113.77/32`

Existing inbound and outbound rules remained present.

## 7. Security Safeguards

The test retained the following safeguards:

- Automatic containment remained disabled.
- The dedicated non-default test NACL was used.
- The approved test subnet association was checked.
- The destination IP was validated.
- Protected IP checks were performed.
- Duplicate rules were rejected.
- Only one rule was created during the direct function execution.
- The configured NACL rule-number range was respected.

## 8. Test Conclusion

The outbound detection, parser classification, Lambda validation, and LocalStack NACL API remediation stages were successfully demonstrated.

The test confirms that the remediation function can create an outbound DENY rule for a validated destination IP.

**Limitation:** LocalStack API acceptance and NACL configuration verification do not demonstrate actual packet blocking. This environment does not provide a real AWS VPC data plane for validating traffic enforcement. The result must therefore be described as an API-level remediation test, not proof of production network containment.

The Lambda handler's automatic-containment setting remains disabled.
